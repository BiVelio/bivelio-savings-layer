# Bitácora — 2026-07-20 · Revocation call-home + enforcement en vivo (never-brick)

## Qué se hizo hoy
Se añadió el **kill-switch de media vida** que faltaba: una licencia **cancelada/revocada antes de su `expires_at`** ahora **deja de funcionar en un proceso en marcha**, sin reinicio y **sin brickear nunca** la producción del cliente si el control-plane está inalcanzable. También se cerró un hueco latente: el gate offline `licenseKey` era de **reloj congelado** (una licencia expirada seguía funcionando hasta reiniciar) → ahora es de **reloj vivo**.

El diseño se presionó con un **panel de 3 perspectivas** (security / availability / minimal-surface) + síntesis antes de escribir código. Decisiones de producto (con el usuario):
1. **SLA de revocación ~15 min** por defecto (`pollIntervalSeconds=900`, `floorSeconds=300`, jitter ±10%, backoff hasta 3600).
2. **Arreglar el expiry offline en este cambio** → gate offline pasa a reloj vivo (unificado en `liveGateFromKey` con snapshot vacío).
3. **`GET /licenses/revocations` público** — la integridad viene de la firma Ed25519 (solo expone UUIDs opacos `jti`); rate-limiting a nivel plataforma.

## Decisiones de diseño (locked)
- **Fetch-failure = FAIL-OPEN.** Un poll fallido/manipulado/stale/rolled-back es un **no-op** que mantiene el último snapshot bueno. `generate()` deniega SOLO por: firma inválida, expiry pasada la gracia (del propio token, sin red), o `jti` en el snapshot firmado **sticky**. Los dientes de seguridad son el snapshot **grow-only + monotónico (`seq`) + firmado**, no fail-closed. Residual documentado: quien aísla el CP *antes* de observar una revocación conserva premium hasta `expires_at+grace` (irreducible para cualquier SDK offline-first que honre never-brick).
- **Firmar la lista.** El **cliente es el adversario** y controla su egress (proxy TLS / CA corporativa / DNS override) → HTTPS no basta. Firma desprendida Ed25519 (clave privada solo en el CP) impide stripping/forja/rollback. Verificada **offline** con `@noble/curves` contra la MISMA clave pública embebida.
- **Formato de wire = token compacto** `base64url(header).base64url(body).base64url(sig)`, header `typ:"BVSALA-REVOC"` → **domain separation** (un license token no se puede replayear como lista de revocación). Reusa el mismo primitivo de verificación que las licencias, así node (`node:crypto`) y browser (`@noble/curves`) coinciden byte-a-byte.
- **Seam C.** El path `licenseKey`-solo sigue **offline/zero-network** (byte-idéntico salvo el reloj vivo); `licenseServerUrl` opt-in construye poller + live gate enteramente en `src/license/*` con `fetch` global inyectable (patrón de `openai-compatible.ts`), **sin imports `node:`**; el `licenseGate` inyectado sigue ganando (escape hatch avanzado, ahora vivo vía `LicenseClient.setRevoked()/refresh()`).

## Cómo llega la revocación al enforcement (0 cambios al pipeline)
`assertLicensed()` ya consulta `gate.isActive()/status()` en vivo en cada `generate()`. Cadena: CP `revoke(jti)` → `revision++` → `GET /licenses/revocations` firma lista con nuevo `seq`+jti → poller `verifyRevocationList(minSeq=snapshot.seq)` → `snapshot.apply()` (union sticky) → siguiente `generate()` → `deriveStatus(payload, now(), snapshot)` ve el jti → `"revoked"` → `LicenseError`. El request path del cliente nunca toca la red (lee un Set en memoria).

## ⚠️ Requisito para producción (durable RevocationStore)
El `InMemoryRevocationStore` es solo CP-0. Un store durable (Postgres) **DEBE**: (a) persistir el set **y** una `revision` monotónica a través de cold starts; (b) hacer que el endpoint devuelva **503 (no una lista vacía auténtica)** hasta estar hidratado — si no, un cold start firmaría `seq:0, revoked:[]`, que todo cliente con un seq mayor rechaza como rollback (bien) pero que además frena la propagación de revocaciones nuevas. Documentado en `services/licensing/src/service.ts`.

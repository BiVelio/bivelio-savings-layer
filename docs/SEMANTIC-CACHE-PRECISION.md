# Semantic cache precision

> Generated by `pnpm cache-semantica:publicar` from the measurement artifact `benchmarks/evidencia/cache-semantica-2026-09-27.json` (sha256 `50417d554550bf23093a5d2d1e149be4e0abb8e212923aab3b15422c3a22bcd3`). Every figure on this page is read from that file; do not edit it by hand.

Measured on 2026-09-27 at commit `7c14ba33315c46c32c29a4c3e828e6b3506c9735`, SDK 0.4.24, Node v25.9.0. No model was called and no credential was used: the provider is a stand-in, and the only network traffic was the download of public datasets at pinned revisions.

## What is measured

The semantic cache as it ships, driven through the whole layer (`createSavingsLayer`), not a re-implementation: the built-in embedder, the default floors, the deterministic guard that compares figures, dates, negations and content overlap turn by turn, and the policy that decides whether a request may use the cache at all.

- Embedder: `built_in` (lexical: it scores word overlap, not meaning).
- Similarity floor: 0.72 (a stored request below it is not a candidate).
- Accept floor: 0.85 (the confidence a hit must reach; with no verifier configured, confidence is the similarity).
- Effective floor: **0.85**, the higher of the two: confidence is the lower of the similarity and the verifier's score, so a hit needs a similarity at or above both floors. No verifier is configured here.
- Records kept: 5,000 (the default), evicted first in, first out.
- Only the semantic cache is on (`exactCache: false`, `deterministicResolvers: false`), so every reuse counted here is a semantic one. In a default setup the exact cache would answer a repeated request first.

A **reuse** is a request answered with a stored answer instead of a provider call. **Precision** is the share of reuses that were right to make. **Recall** is the share of the requests that could have been reused that were.

## Headline

**Precision floor: 91.0 %.** That is the lower end of the 95 % Wilson interval for precision on the `arena` triplets: 58 of the 59 reuses were compatible with the request they answered (point estimate 98.3 %).

Recall on the same cases: 13.6 % [10.6 % – 17.1 %]. The cache reused 58 of the 428 requests labeled reusable; the rest went to the provider, as they would without the cache.

## A. Triplets: GPTCache reuse_compatibility

Each case is a stored request, its stored answer and a new request, with a label saying whether the stored answer can be reused as is for the new request. Each case runs in its own tenant, so cases are independent and the intervals are Wilson score intervals. Cases labeled `uncertain` are left out of precision and recall and counted apart.

## B. Stream: SemBenchmarkLmArena

The first 20,000 prompts of the pinned revision, in dataset order, through one layer and one tenant. The stand-in provider answers with the class (`ID_Set`) of the prompt it was asked, so a reuse is correct when the class it serves is the class of the prompt, the dataset card's definition of a correct hit. Whether a prompt is reused depends on what earlier prompts left in the cache, so prompts are not independent: the intervals come from resampling whole classes (2,000 resamples, fixed seed 20260927, 3,017 classes).

| Measure | Value [95 % CI] | Count |
|---|---|---:|
| Reuse rate | 14.5 % [13.7 % – 15.3 %] | 2,359 / 16,316 prompts |
| Precision | 90.3 % [88.0 % – 92.6 %] | 2,130 / 2,359 reuses |
| Wrong reuse rate | 1.4 % [1.1 % – 1.8 %] | 229 / 16,316 prompts |
| Recall vs reachable | 17.7 % [16.8 % – 18.6 %] | 2,130 / 12,062 prompts whose class was already cached |

- Records kept: 5,000; 8,957 were evicted during the run. The policy kept the cache out of 3,684 prompts, which are left out of every row above.
- 48 of the 229 wrong reuses served a stored prompt **identical** to the prompt asked, which the dataset files under a different class; 74 distinct prompts appear under more than one class in the rows used. Those count against precision here, but they are label noise, not a cache error.

## Context: the project's own evaluator

On the same 512 cases, the project's own evaluator (JEV, an LLM judge) at threshold 0.70, recomputed from `baseline_jev_070.jsonl` with this scorer: precision 100.0 % [98.9 % – 100.0 %], recall 82.9 % [79.1 % – 86.2 %]. It is the project's evaluator, not this SDK's: it asks a model about every candidate, and its threshold was calibrated on this dataset (both per the project's README). It is shown to place the figures above, not as a comparison on equal terms.

Scorer self-check: on all the triplets, the scorer used on this page reproduces the project's published figures for that evaluator exactly (364 of its 365 reuses correct, 364 of the 505 cases labeled reusable).

## What this means for you

- **Precision is the number to read.** A wrong reuse serves the answer to a different question and nothing downstream flags it; a missed reuse only costs the provider call you would have made anyway.
- **It is opt-in three times over:** `savings.semanticCache` on the request, a `semanticCache` passed to `createSavingsLayer`, and the `semantic_cache` feature on your license.
- **It stays off on agentic traffic** (requests that declare tools, carry tool calls or tool results, or hold more than one user turn) unless you set `savings.semanticCache: "include-agentic"`.
- **Measure it on your own traffic before you rely on it.** Every semantic reuse reports its similarity and the floors it cleared in `report.qualityLedger.cacheMatch`, and `report.qualityStatus` marks it `task_equivalent`, never `exact`.
- This page measures whether a reused answer was right to reuse. It does not measure, and does not claim, what a reuse saves.

## Limitations

- **The triplet labels are model-assisted**, not a human gold standard, as the project's README states. Label sources among the measured cases: `first_model_review` 370, `second_model_adjudication` 136, `manual_scope_override` 6.
- **The labels judge reuse compatibility, not correctness.** They check whether the stored answer fits the new request (task, entities, numbers, versions, explicit constraints, format, completeness), not whether that answer is factually right. Some wrong reuses are wrong because of the stored answer rather than the question; the category table above shows which.
- **The triplets are pre-selected pairs.** They are the candidate pairs of the original experiment, already picked by semantic retrieval, so their reuse rate is not a production reuse rate (the project's README says the same).
- **Lexical embedder.** The built-in embedder sees word overlap only. Passing your own `embed` changes precision and recall in ways this page does not measure.
- **The stream's rewordings are model-written.** Per its dataset card, each class is one real LM-Arena prompt plus variants generated by a model, not repeats observed in real traffic.
- **The stream is one ordering of one dataset.** Its figures depend on the order of the prompts and on the record limit; label noise (identical prompts under different classes) lowers its measured precision.
- **Not measured:** the two triplet arms whose prompts come from ORCAS (`search_llama`, `search_gpt`) and SemBenchmarkSearchQueries, because ORCAS is licensed for non-commercial research only (see below).
- One model id is used for every request, served by the stand-in provider; it only takes part in the cache identity.
